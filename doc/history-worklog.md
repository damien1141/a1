- `internal/agent/executor.go`: per-round call allowance. `SetCallAllowance(n)` (n<0 = unlimited) resets round counters; `claimCall()` atomically reserves a slot before ANY execution work (before ext PreTool/gate/ask, and before the InProgress row is emitted, so an over-budget call neither prompts nor flashes). Over-budget calls return `rejectResult` with "tool call budget reached (N tool calls per turn) …". `AllowanceUsed()` = granted count; `AllowanceTripped()` = at least one call was rejected for budget. Atomics because read-only batches claim slots from parallel goroutines. Zero-value hazard fixed: allowance 0 would read as "reject everything", so `NewExecutor` initializes it to -1 (unlimited) — direct-constructed executors (existing tests) keep the old behavior.
- `internal/agent/engine.go` + `option.go`: `WithMaxToolCalls(n)` option, `SetMaxToolCalls`/`MaxToolCalls` (atomic.Int64 — safe to change mid-loop, effective next round). The Loop tracks `toolCallsUsed` per turn (reset every Loop), computes the per-round allowance = limit − used, clamps at 0, and skips the whole mechanism when the limit is 0 (default) OR the gate is yolo (`permission.ModeOf(engine.gate) == ModeYolo` — yolo promises unlimited, so the budget never fights an explicit mode choice; the check re-reads the gate each round, so toggling yolo mid-session flips the behavior immediately). When `AllowanceTripped()` after a round: append a user-role note "System note: tool call budget (N) reached — the turn was stopped. Raise the cap from the command palette (Max tool calls) or ask to continue." to the session AND yield `session.UserAppend` (renders in the transcript, persists in the session JSONL so the model sees why the turn ended on the next prompt), then end the turn cleanly — no error, unlike the round budget's ErrMaxRounds.
- `internal/project/config.go`: `ToolsConfig{MaxToolCalls int}` on Config; `tools.max_tool_calls` in fileConfig (pointer → absent key stays unlimited); `SetMaxToolCalls(global, n)` — surgical yaml.Node edit (reuses modifyConfigYAML/getOrCreateMapping/setScalar; scalarNode learned the int/!!int case) preserving comments/key order, mirroring SetDangerouslyAllowAll. n<=0 removes the key and prunes an empty tools block (unrelated keys under tools survive).
- `internal/configserver/server.go`: `ToolsDoc` on ConfigDoc so the editor's full-file rewrite round-trips the key; POST /api/config carries the file's existing tools block over when the payload omits it (the editor page has no tools form — without this, every editor save would wipe a palette-set budget). Explicit payload values still win.
- `internal/tui/controller/controller.go`: `maxToolCalls` atomic seeded from config at NewController; `openEngine` passes `WithMaxToolCalls`; `MaxToolCalls()` accessor; `SetMaxToolCalls(n)` = store + live-engine rebind (`engine.SetMaxToolCalls`) + `project.SetMaxToolCalls` persist.
- `internal/webserver/server.go`: `engineOptions` now passes `WithMaxToolCalls(s.proj.Config().Tools.MaxToolCalls)` so web-surface engines honor the persisted budget too (yolo still overrides engine-side).
- `internal/tui/commands/toolbudget.go` (new, registered in builtins.go): one command `maxtoolcalls`, both surfaces. Ctrl+K palette: Noun "settings", Verb "max tool calls", submenu "Max Tool Calls (per turn)" with ✓-marked unlimited + presets 10/25/50/100 + "custom…" pushing a finer ladder (5/15/20/30/40/60/75/150/200/250/500/1000). Slash: `/maxtoolcalls 42` (arbitrary), `/maxtoolcalls unlimited|off|none|0`, bare shows the current value; ArgCompleter suggests presets. Toasts confirm ("Max tool calls: 25 per turn (yolo overrides with unlimited)") and surface save errors.
- Tests: `internal/agent/toolbudget_test.go` (budget stops turn cleanly with note + rejected stubs; unlimited by default; yolo overrides; batched round consumes multiple slots; mid-loop SetMaxToolCalls takes effect; executor allowance on concurrent read-only batch 2-of-5; unlimited executor). `internal/project/toolbudget_config_test.go` (parse, absent-key, persist preserves comment/models/order, zero removes + prunes, other tools keys survive). `internal/configserver/config_tools_test.go` (editor save carries the budget over; explicit payload wins). ## Yolo mode turns off the bash sandbox

User request: "Can you make it so the yolo permission mode turns off the bash sandbox — sometimes I need to look at system binaries."

- `internal/permission/gate.go`: `sandboxEnforcing` returns false for a yolo policy before the setting/host switch ever runs. The checkBash containment branch ("containment substitutes for approval") therefore never answers for a yolo run — before, it returned Allow with a "sandboxed: writes confined to the workspace" note, which after this change would have described walls the exec side never raised. Decision outcomes are unchanged (yolo's fold already turned the would-be Ask into Allow); what changes is the mechanism report. Comment block updated to name yolo among the contracts that beat containment.
- `internal/tools/bashtool/sandboxed.go`: `bashSandboxProfile` consults `sandboxSuppressedByMode` before the off/backend checks — the new helper resolves the effective mode as "live context mode if attached, else the config file's `permissions.mode`" and suppresses the profile when it is yolo. Foreground (`bash.go`) and background (`background.go`) both flow through here.
- `internal/tools/bashtool/background.go`: `startBackground` carries the calling context's permission mode into the detached context alongside the cwd (same pattern, one more value). Without this, a background shell launched from a yolo turn would have been the one place the sandbox kept enforcing.
- `internal/tools/tooldef/context.go`: `WithPermissionMode`/`PermissionModeFrom` — the context seam the executor uses to publish the live mode. Keyed on a plain string: tooldef sits below permission in the import graph, and importing the gate package there would drag it into every tool's dependency set for one constant.
- `internal/agent/executor.go`: `runOneChecked` attaches `permission.ModeOf(e.gate)` to the tool context next to WithCwd/WithImageEnabled. The mode a tool sees is the mode that gated it — the TUI's SetPermissionMode and the web switcher's rebuildGate both swap the engine's gate on a mode change, and SetPermission propagates to `engine.executor.gate`, so a mid-session shift-tab cycle or web dropdown flip takes effect on the next bash call without a config rewrite. ModeOf unwraps SessionAllowGate; AllowAll attaches nothing (config fallback answers).
- `internal/permission/policy.go`: ModeYolo and Policy.Sandbox doc comments state the new contract (and why it is coherent: yolo is a mode, not an allow-all flag — the deny list and the APPA trajectory still fire).
- `internal/sandbox/sandbox.go`: package doc reworded — the old "'yolo with walls' becomes a real mode" line described the opposite of the new semantics; containment is now framed as autopilot's walls (the walls-on cousin of yolo), with yolo explicitly wall-less.
